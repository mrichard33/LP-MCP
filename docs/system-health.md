# System health monitoring

One place that answers "is every part of the lead → dialer → appointment
pipeline working right now, and if not, what is it costing us?". Built in
phases (handoff 2026-10-14). Phase 0 (this doc) is the recording layer; Phase 1
adds incidents and the command center.

## The pieces

| Piece | Where | What it does |
|---|---|---|
| Registry | `health_checks` (LP database) | One row per check: question, severity, cadence, active window, warn/fail rules, thresholds in `config`, `mode`, owner job. **The database is the source of truth.** |
| Results | `health_results` | One row per evaluation: `pass` / `warn` / `fail` / `unknown` / `skipped`, a value, a ≤300-char summary, a ≤8 KB detail, a fingerprint. |
| Latest | `v_health_check_latest` | Latest result per check and its color. No result, or one older than `stale_after_min`, is red (P1) or yellow: silence is never green. |
| Systems | `v_system_status` (live checks) / `v_system_status_shadow` (all) | One row per system: lead_perfection, five9, ghl, supabase, n8n, railway, ai_agents, webhooks. |
| Incidents | `incidents`, `incident_events`, `v_incident_board` | Phase 1. One open incident per fingerprint (partial unique index). |
| Retention | `health_results_daily` | Phase 1. Daily rollup of results older than 30 days. |

Schema history: `supabase/migrations/20261015120000_system_health.sql` (applied to
prod by hand on 2026-10-14; the file is idempotent). Registry seed:
`sql/seeds/health_checks.sql`, generated by `node scripts/export-health-checks.js --sql`,
which also writes `src/health/registry.snapshot.json` for review diffs.

Access is service_role only (RLS on, no policies, anon/authenticated revoked on
the tables and the views): `detail` names leads.

## How a result gets written

- **Existing watchdogs** return `health: [...]` next to what they already
  return; `runJob` (`src/job-runner.js`) writes each entry with the run's
  `job_run_id`. Nothing they post to Slack changed. The builders are pure, in
  `src/health/watchdog-results.js`. The reply-SLA watchdog and the executor
  heartbeat are not under `runJob`; they call `recordThrottled` (at most once a
  minute, or 5 for the reply SLA).
- **The `health-checks` job** (`src/jobs/health-checks.js`, every 5 min,
  `HEALTH_CHECKS_MODE` off|shadow|live, default shadow) evaluates the checks it
  owns. Each check runs on its own cadence inside the tick, capped at 5 s, in its
  own try/catch. A check whose owner job is not built yet (synthetic canaries,
  the n8n poller) gets an hourly `unknown` naming why.
- **The recorder** (`src/health/record.js`): `recordHealthResult` never throws,
  refuses a check id the registry does not have, a status outside the five, and
  a fingerprint carrying a live value (`31 min`, `12 leads`, `95%`, a
  timestamp). An entry may give `status`, or give its tri-state `active` plus a
  `value` and let the check's config decide the band (`evaluate`), or a
  `rule(value, config)`. Thresholds therefore live in `health_checks.config`.

## The rules

- **Could not tell is never a pass.** A failed read, a timeout or a missing
  config is `unknown` with the reason.
- **Outside a check's `active_window` the result is `skipped`.** The dialer is
  quiet at 22:00 because nobody dials, not because it is healthy, and an
  `unknown` every night would paint the board yellow.
- **A check with several members** (one result per campaign, per LP report)
  writes one row per member, each with its own fingerprint.
- **Five9 is the only source of truth for calls** (`five9_events_raw`), never
  LP call counts.
- **Read-only** against LP, Five9, GHL, n8n and Railway.

## Modes

Two switches, on purpose:

- the job's env var (`HEALTH_CHECKS_MODE`, later `DIALER_SLA_MODE`,
  `APPT_PIPELINE_MODE`, `INCIDENT_NOTIFIER_MODE`): off stops the job.
- each check's `mode` column: `shadow` writes results only; `live` lets the
  incident notifier (Phase 1) open incidents and post cards. Flip family by
  family (lead, dialer, appointment first) after 5 business days of
  `v_health_check_latest` with no false red.

## Phase 1: incidents and the command center

| Job | File | Mode (default) | What it does |
|---|---|---|---|
| `dialer-sla-check` | `src/health/dialer-sla.js` | `DIALER_SLA_MODE` (shadow) | list membership vs the routing intent (`src/dial-routing-intent.js`, the same decision both routing jobs make), first dial, stalled lists, dial-rate drop, 3 dials in 24h, never-again. |
| `appointment-pipeline-check` | `src/health/appointment-pipeline.js` | `APPT_PIPELINE_MODE` (shadow) | inbound queue age, issued by 20:15, a rep on every confirmed visit, Set vs confirmed, Conf dial coverage, capacity, dupes, time rules, required fields. |
| `incident-notifier` | `src/jobs/incident-notifier.js` | `INCIDENT_NOTIFIER_MODE` (shadow) | results → incidents; ONE Slack card per incident, edited in place. |
| `health-retention` | `src/jobs/health-retention.js` | `HEALTH_RETENTION_MODE` (dry_run) | 30-day rollup, n8n / synthetic age-out, lead_leak_daily summarized before its 90-day delete. |

**Incidents** (`src/health/incidents.js`). One non-terminal incident per
fingerprint. Every move is in `TRANSITIONS` (anything else throws) and writes an
`incident_events` row naming the actor (`system`, `aios`, or a person's email).
A pass moves an open incident to `verifying`; 2 passes in a row resolve it (1
for a daily check); a fail inside `verifying` reopens it, and 3 reopens in 24h
mark it flapping. Closing with no action quiets the fingerprint for 7 days
(`health_checks.config.suppress`).

**Cards.** Only a check in `mode='live'` opens an incident from a result. The
card posts once the incident is still failing 10 minutes after it opened (a
daily check at once), to #ops-alerts, and P1 lead / dialer / appointment cards to
#contact-center too. Unknown on a P1 live check for 30 minutes opens a P2
"could not read" incident. Unacknowledged cards get a thread reminder from
`escalation_policy`; a step with no `to` is skipped and logged once.

**Legacy alerts** (`src/health/alert-key-map.js`). `drift:ghl_closed_lp_active:*`
(one incident for the whole set), `ci:recording_archive_unreachable` and
`capacity_ranker:campaign_not_running:*` keep an incident in step and set
`alert_conditions.incident_id`. Their own cards still post until
`LEGACY_ALERT_SUPPRESS_MAPPED=true` with the notifier live.

**Doors** (`src/health/ops-actions.js`, one module): `POST /ops/incidents/:id/{ack,snooze,close,run}`,
`POST /ops/checks/:check_id/run`, `POST /ops/checks/run-all` (bearer token, `actor`
in the body; snooze and close need a reason), the MCP tools `incident_action`
and `health_run_check` (the dashboard), and the Slack buttons `incident_ack` /
`incident_snooze`, handled in LP-MCP and never forwarded to n8n's onboarding
flow (it reads any unknown button as a member approval).

**Gaps #14** (from `raw_lp_data`): issued = `issued` / `everissued` /
`netissued` ("true"/"false" strings, also `lp_leads.ever_issued`); Rank / Appt
Type = `rank` / `rnk_id`; Products / Qty = `productid`, `prod2..4`, `qty..qty4`.
Rep viewed / acknowledged is not in LP's data, so `appt.rep_not_acknowledged`
reads unknown.

## Going live

Five business days in shadow, then, one at a time: set `mode='live'` on the
lead, dialer and appointment rows of `health_checks` (family by family), flip
`HEALTH_CHECKS_MODE`, `DIALER_SLA_MODE`, `APPT_PIPELINE_MODE`, then
`INCIDENT_NOTIFIER_MODE=live`. Before each flip, read `v_health_check_latest` for
that family: no red that was not a real problem.

## Adding a check

1. Insert the row in `health_checks` (mode `shadow`), with thresholds in
   `config` and an `owner_job_id`. Re-export: `node scripts/export-health-checks.js --sql`.
2. Either return it from the owning job as `health: [...]`, or add it to
   `CHECKS` in `src/jobs/health-checks.js` (`{ everyMin, run(ctx, row) }`).
3. `scripts/test-health-registry.js` fails if code names a check the registry
   lacks, or a check's owner is not a registered (or planned) job.

## The words people read (2026-10-15)

Every summary, Slack card and digest line is plain English, written with
`src/health/plain.js`:
- Eastern time on a 12-hour clock ("8:45 PM"), never "20:45 ET".
- Durations a person would say ("about 19 hours", not "1125 min").
- Severity as a word: P1 Urgent, P2 High, P3 Medium, P4 Low. The codes stay in
  the database.
- No check ids, "p90", "SLA" or "parity" in anything a person reads.

The registry's label, question, yellow/red rule and "why it matters" text is
plain too (`sql/seeds/2026-10-15_health_checks_plain_english.sql`). `cadence`
and `active_window` keep their machine form ("08:00-20:00 ET"), because code
reads them; the dashboard shows them as 12-hour time.
`scripts/test-health-plain-results.js` fails if a summary carries a 24-hour time.

Three checks changed behaviour in the same pass:
- **Services running on Railway** (`svc.railway_restarts`) asks Railway for each
  service by ID (`src/health/railway-state.js`). The old lookup searched
  LP-MCP's own project by name and showed "?" for HL-MCP, n8n and the dashboard.
  Red when a service is down. Yellow for a failed update (the previous version
  still runs), 4+ restarts in an hour, or a service it can't see.
- **Evening appointment checks** run on demand before their first time today
  write nothing and answer "Not due yet: runs at 7:30 PM and 8:15 PM."
- **Lead Perfection sync errors** turn red only for new errors (10+ today or 5+
  in an hour); old open ones are yellow. **Appointments with no result** counts
  the last 14 days only.
